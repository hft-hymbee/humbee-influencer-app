# 04 — Design tokens and theming

## 4.1 The source of truth

`design_handoff_humbee_influencer_app/design/tokens/` — four CSS files, 1,624 lines, exported from
`HUMBEE_Design_System.fig` (531 variables):

| File | Lines | Content |
| --- | --- | --- |
| `fig-tokens.css` | 1,497 | The raw Figma variable export. Colours as hex, numbers as **unitless floats** |
| `semantic.css` | 58 | Aliases that wrap the floats in `calc(var(--x) * 1px)` and name brand roles |
| `typography.css` | 65 | The type ramp — size / line-height / weight triples |
| `fonts.css` | 4 | Lato faces |

The handoff is explicit (docs/02): *"port them to your platform's token format rather than retyping
values."* Retyping 531 values by hand guarantees drift and typos in a spec where "fidelity is not
negotiable".

## 4.2 The generator

`scripts/gen-tokens.ts` parses the CSS custom properties and emits typed TypeScript. It resolves
`var()` references and evaluates the `calc(var(--n) * 1px)` wrappers to plain numbers, because React
Native styles take unitless numbers.

```ts
// src/shared/tokens/colours.ts — GENERATED by scripts/gen-tokens.ts. Do not edit.
export const colours = {
  primary100: '#995A00',
  primary200: '#7A4800',
  primary50:  '#CC9A4D',
  primary25:  'rgba(153,90,0,0.25)',
  primary10:  'rgba(153,90,0,0.10)',
  primary5:   'rgba(153,90,0,0.05)',
  secondary100: '#FFA525',
  neutralWhite: '#FFFFFF',
  neutral10:  '#F2F2F2',
  neutral25:  '#E5E5E5',
  neutral50:  '#D9D9D9',
  textTertiary: '#8C8C8C',
  textSecondary: '#666666',
  textPrimary: '#333333',
  base:       '#0D0D0D',
  success100: '#008000',
  success200: '#006600',
  error100:   '#CC0000',
  warning200: '#BF8000',
  info100:    '#0081F2',
  info200:    '#0067C1',
  illustrationTint: '#EDF1F6',
} as const;

export type ColourToken = keyof typeof colours;
```

Three properties matter more than the shape:

1. **`as const` plus a derived key type.** `colours.chestnut` is a compile error. So is a raw
   `'#995A00'` passed to a prop typed `ColourToken`. Handoff rule: *"Never introduce a colour that is
   not in the token file"* — now the compiler owns that rule instead of the reviewer.
2. **Names mirror the design system**, not their appearance. `primary100`, never `brown`. A designer
   reading a Figma variable panel and a developer reading a style object say the same word.
3. **Regenerated in CI.** `pnpm gen:tokens && git diff --exit-code` fails the build if someone
   hand-edited a generated file or if the design system moved without the app following.

## 4.3 Typography

The handoff defines 17 named type roles and one hard prohibition: *"There is no 14px body size in the
system. Do not introduce one."* Encode the roles, not the numbers.

```ts
// src/shared/tokens/typography.ts — GENERATED
export const type = {
  screenTitle:    { fontFamily: 'Lato-Bold',     fontSize: 24, lineHeight: 32 },
  headerTitle:    { fontFamily: 'Lato-Bold',     fontSize: 17, lineHeight: 24 },
  headerSubtitle: { fontFamily: 'Lato-Regular',  fontSize: 13, lineHeight: 18 },
  sectionHeading: { fontFamily: 'Lato-Bold',     fontSize: 20, lineHeight: 28 },
  statValue:      { fontFamily: 'Lato-Bold',     fontSize: 20, lineHeight: 26 },
  bodyLarge:      { fontFamily: 'Lato-Regular',  fontSize: 15, lineHeight: 22 },
  rowTitle:       { fontFamily: 'Lato-Bold',     fontSize: 15, lineHeight: 20 },
  leaderName:     { fontFamily: 'Lato-SemiBold', fontSize: 15, lineHeight: 20 },
  body:           { fontFamily: 'Lato-Regular',  fontSize: 13, lineHeight: 20 },
  bodyBold:       { fontFamily: 'Lato-Bold',     fontSize: 13, lineHeight: 18 },
  overline:       { fontFamily: 'Lato-Bold',     fontSize: 11, lineHeight: 20, letterSpacing: 0.5, textTransform: 'uppercase' },
  meta:           { fontFamily: 'Lato-Regular',  fontSize: 11, lineHeight: 16 },
  tableHeader:    { fontFamily: 'Lato-Bold',     fontSize: 11, lineHeight: 16, letterSpacing: 0.6, textTransform: 'uppercase' },
  navLabel:       { fontFamily: 'Lato-Bold',     fontSize: 10, lineHeight: 14 },
  otpDigit:       { fontFamily: 'Lato-Bold',     fontSize: 24, textAlign: 'center' },
} as const;
```

Notes that will otherwise cost a day each:

- **Weight comes from `fontFamily`, not `fontWeight`.** On Android, `fontWeight: '600'` against a
  named custom font silently synthesises or falls back. Ship three separate faces and name them.
- **`includeFontPadding: false` on every `<Text>`.** Android adds font padding above and below the
  glyph box; without disabling it, a 13/20 line renders taller than 20 and every vertical rhythm in
  the spec is off by 1–3px. Bake it into a `Text` wrapper in `shared/ui` so nobody forgets.
- **`textAlignVertical: 'center'`** for single-line rows on Android, same reason.
- Ship exactly one `Text` component. Raw `react-native` `Text` should be lint-banned so no screen can
  render an unstyled 14px system-font string.

## 4.4 Borders and elevation — the two RN translation traps

**Borders.** The handoff mandates `inset 0 0 0 1px #E5E5E5` — inset box-shadows, *"never CSS
borders, so they never affect layout"*. React Native has no inset shadow. The equivalent that
preserves the design's intent is `borderWidth` with `boxSizing`-safe layout:

```ts
// shared/ui/Card — the RN translation of `inset 0 0 0 1px #E5E5E5`
card:         { borderWidth: 1,   borderColor: colours.neutral25, borderRadius: radius.m },
cardSelected: { borderWidth: 2,   borderColor: colours.primary100, ...elevation[2] },
currentUser:  { borderWidth: 1.5, borderColor: colours.primary100, ...elevation[2] },
rowHairline:  { borderBottomWidth: 1, borderBottomColor: colours.neutral10 },
```

In React Native, `borderWidth` is drawn **inside** the view's bounds and does not expand it — so the
inset-shadow intent holds. The one place it differs is the 1px → 2px change on selection: on the web
prototype the ring thickens with no reflow; in RN the content box shrinks by 1px on each side. Fix it
by giving the unselected state `borderWidth: 2` with `borderColor: 'transparent'` **or** by keeping
padding constant and accepting the 1px, per component. Decide once in `Card` and `PickCard` and
document it there — this is the most likely source of "the selected card jumps" bug reports.

**Elevation.** `0 1px 3px rgba(0,0,0,0.15)` does not translate directly. iOS takes
`shadowColor/Offset/Opacity/Radius`; Android needs `elevation` and, on the New Architecture, honours
`boxShadow` on recent versions. Generate a platform-split object once:

```ts
export const elevation = {
  1: Platform.select({
    ios:     { shadowColor: '#000', shadowOffset: { width: 0, height: 1 }, shadowOpacity: 0.15, shadowRadius: 3 },
    android: { elevation: 2 },
  }),
  2: Platform.select({
    ios:     { shadowColor: '#000', shadowOffset: { width: 0, height: 2 }, shadowOpacity: 0.15, shadowRadius: 8 },
    android: { elevation: 4 },
  }),
} as const;
```

Android `elevation` also implies a z-order change and requires a non-transparent background to render
at all — both worth a comment in the file, because a shadow silently vanishing on a transparent view
is a classic hour lost.

## 4.5 Why not NativeWind / Tailwind

Considered and rejected for this specific project:

- The design system is **531 named variables with exact semantics** (`primary25` is "card ring on
  hover, podium panel ring"). Tailwind's value is a compact utility vocabulary for ad-hoc layout;
  here the vocabulary already exists and is authoritative. Mapping one onto the other adds a
  translation layer whose only output is class strings.
- `className="bg-primary-100 rounded-m px-4"` is **not type-checked against the design system** the
  way `colours.primary100` is. The strongest guarantee in §4.2 — you cannot compile a non-token
  colour — is exactly what a string-based API gives up.
- Runtime cost. Even with a compile step, class resolution is work `StyleSheet.create` has already
  done at module load, and the target device has none to spare.

Reconsider if a React web influencer portal appears and shared styling across web and native becomes
worth more than compile-time token safety. Not before.

## 4.6 Theming

There is **no dark mode in v1** and no theme switch. The design is white-first by decision
(handoff docs/02: `#F7F7F7` is the DS page background and *"not used — this app is white-first"*).

Do not build a theme provider "for later". Do keep every colour behind a token so that adding one is
a change in `shared/tokens/`, not a grep across 10 screens. That is the whole cost of the option, and
it is already paid by §4.2.

Two theming-adjacent things that *are* v1 requirements:

- **`prefers-reduced-motion`.** Read via `AccessibilityInfo.isReduceMotionEnabled()` and expose a
  `useReducedMotion()` hook. See `07-animation-and-motion.md` §7.5.
- **Font scaling.** The design specifies exact type sizes and a 44×44 minimum touch target. Users on
  cheap Android phones do enlarge system fonts. Decide per component: cap with
  `maxFontSizeMultiplier` on dense chrome (nav labels, table headers, chips) where a 1.3× scale would
  break the layout, and allow scaling on body copy. Do not set `allowFontScaling={false}` globally —
  the audience needs it, and a blanket disable is an accessibility regression, not a fidelity win.
